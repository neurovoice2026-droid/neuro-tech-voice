# Slice A2: platform settings, safety, dynamic variables and config rollout

This slice covers what the platform owns in every tenant's ElevenLabs agent: call limits and the wait queue, guardrails, privacy and transcript redaction, the LLM in use, dynamic variables and their protection from tenant text, mixed routing modes, pausing, error classification, reconcile, and the rollout of platform changes to existing agents.

Every endpoint, field path, enum and limit below was checked against the official OpenAPI document (`elevenlabs-spec/openapi.json`, downloaded 2026-10-07). `tests/elevenlabs-spec-contract.test.ts` validates the generated bodies against the Create Agent schema, including every new block (paused variant, mixed routing, all content guardrails on, redaction off, `trust_context: low`, cascade off). Vendor behaviour that could only be read from the spec or the docs is marked **unverified live**.

## 2. Error classification (429)

The errors doc documents three 429 codes: `rate_limit_exceeded`, `concurrent_limit_exceeded` and `system_busy`. The per-agent limits (`agent_concurrency_limit`, `daily_limit`) have **no documented code**. `classifyHttpError` therefore uses these rules:

* A documented workspace code is `rate_limited`, a health signal for the shared circuit, unless its message names the agent ("agent", "daily").
* Any other 429 with the documented body shape (an unknown or agent-specific code, or a message about an agent or daily limit) is the new `tenant_limited`, unless the message names the workspace, subscription, plan or burst capacity.
* A 429 without a structured body stays `rate_limited`, as before.

`tenant_limited` is not retryable and **never a health signal**: one tenant at its own cap cannot open the routing circuit for everyone. On register-call, the router logs `router.tenant_call_limit` and tries the next candidate: Cartesia when configured, otherwise the apology or human handoff. Native numbers have no failover (ElevenLabs rejects or queues the call itself). API routes answer `tenant_limited` with 429 and a safe message.

## 3. Pausing an agent (native numbers)

App-routed calls already honour `is_active` in the router. Native numbers bypass it, so a paused agent is synced as a **paused variant** (`lib/elevenlabs/paused-agent.ts`):

* the first message is the router's localized "unavailable" line (non-interruptible);
* a short prompt says not to converse and to use `end_call`;
* `built_in_tools` keeps `end_call` only, `tool_ids: []` and `language_presets: {}`;
* `turn_timeout` is 3 s, `silence_end_call_timeout` 10 s and `max_duration_seconds` 60.

Platform settings (privacy, limits, guardrails, webhooks, analysis) stay the same. `POST /api/agent/toggle` and `PATCH /api/agent {is_active}` bump the revision and re-sync, but only when an ElevenLabs agent exists: a pause never creates one. Resuming pushes the normal body. The variant is part of the spec, so tenant saves and the rollout keep a paused agent paused. A call to a paused native number is still a short ElevenLabs conversation (a few billed seconds, and a call row). Detaching numbers was rejected: ElevenLabs' behaviour for an unassigned number is undocumented, and it belongs to the telephony binding.

## 5. Migration 014 (`supabase/migrations/014_config_rollout.sql`)

* `agent_provider_resources.rollout_checked_at timestamptz` (nullable), plus the partial index `agent_provider_resources_rollout (provider, rollout_checked_at NULLS FIRST) WHERE status = 'ready' AND external_id IS NOT NULL`.
* No DROP. `ADD COLUMN IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`, so it is safe to re-run. The table has no tenant write policy (migration 010), so no guard trigger is needed. Only the service role writes the column.
* **Verified** on a throwaway PostgreSQL 16 with Supabase-like roles: migrations 001–014 applied, then 014 re-applied. A tenant sees only its own row and its UPDATE of `rollout_checked_at` changes 0 rows. The service role updates it. The rollout scan uses the partial index. `tests/migrations/014-config-rollout.test.ts` checks the file statically.
* **Deploy order:** apply 014 before deploying this code. Without it, the `config_rollout` step fails, isolated and logged, while everything else works.

## 7. UI changes

* Call handling, Privacy card: "Provider default" becomes "Unlimited (kept until deleted)". The help text explains that a shorter period, or turning recording off, also deletes calls already stored at the provider. ## 9. Remaining limitations

* The per-agent 429 code is undocumented. Classification uses the documented codes and message hints (section 2) and needs the live check in step 3.
* Secret placeholders, transcript redaction on non-enterprise workspaces, `trust_context: low` and the PATCH merge semantics are **unverified live**.
* Native inbound calls still get placeholders only (`ntv_call_id: 'unknown'`, token `'none'`): the webhook transfer tool cannot work there. In mixed orgs they now use `transfer_to_number`. The conversation-initiation webhook (telephony slice) would give them real values.
* Plan changes reach the agent through the rollout (one batch per maintenance run; the cron is daily on the Hobby plan), not immediately from the Stripe webhook. Run the admin rollout after a burst of plan changes or after a deploy that bumps the version. To push a change faster, raise `ELEVENLABS_ROLLOUT_BATCH` temporarily.
* Every agent drifts once after this deploy (the hash format and body changed): plan for about N/10 maintenance runs, or force batches through the admin endpoint.
* In the rare case of a cold instance during an LLM catalogue outage, the effective LLM can differ from the cached choice, which can cause one extra re-sync.
* Out-of-band dashboard edits are only overwritten when the local hash drifts. Comparing `version_id` is left for later.
* Other slices that change the agent builder must bump `PLATFORM_AGENT_CONFIG_VERSION` in `lib/elevenlabs/agent-config.ts` so their change rolls out.
