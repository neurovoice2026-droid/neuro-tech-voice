# Slice B1: tool infrastructure (platform webhook tools, transfer, secrets, executions)

This slice turns the one-off `transfer_to_human` webhook tool into reconciled platform infrastructure: typed tool definitions with central behaviour settings, header authentication backed by a workspace secret, race-safe creation, drift repair, execution monitoring and dependent-agent checks. It also makes the transfer itself safe under concurrency and makes failures visible instead of silent.

Every endpoint, field path, enum and limit below was checked against the official OpenAPI document (`elevenlabs-spec/openapi.json`, downloaded 2026-10-07). `tests/elevenlabs-spec-contract.test.ts` now also validates every platform tool config (and a booking-style config using every builder feature) against `WebhookToolConfig-Input`, including the deprecation markers. Vendor behaviour that could only be read from the spec or the docs is marked **unverified live**.

## 2. Authentication of tool requests

| Variable / header | Purpose | Where |
| --- | --- | --- |
| `ntv_call_token` | **Correlation only** (post-call webhook matching needs a non-redacted value). Signed, purpose `'transfer'` (historical name kept so in-flight calls and `call-store.ts` keep matching). Referenced by no prompt and no tool. | register-call and native outbound-call client data (unchanged) |
| `secret__ntv_call_token` | **Tool token**: signed, purpose `'tool'`, distinct from the correlation token, 4 h. Secret variable: never sent to the LLM, usable only in headers, redacted in webhooks. | register-call and native outbound-call client data; placeholder `'none'` (slice A2) |
| `X-NTV-Call-Token` header | `{variable_name: 'secret__ntv_call_token'}` on every platform tool. The route verifies it with purpose `'tool'`: it binds the request to one call, so a tool can never act on another tenant's call. | `api_schema.request_headers` |
| `X-NTV-Tool-Key` header | `{secret_id}` of the workspace secret. Compared in constant time (SHA-256 then `timingSafeEqual`, current and previous key both always compared). Proves the request came from our workspace. Required in production; outside production, a deployment without `ELEVENLABS_TOOL_SECRET` authenticates by the call token alone (warning in diagnostics). | `api_schema.request_headers` |

Shared helper: `app/api/telephony/tools/_lib/elevenlabs-tool.ts` (`authenticateToolRequest`, `allowToolCall`, `sanitizeToolText`, `toolJson`). Responses: 401 with a generic body only for an unauthenticated request (missing or wrong key, or no credentials) and a `webhook_verification_failed` provider event; 400/413/415 for malformed bodies; everything else 200 `{ok, message}`. Per-call budget: 6 tool calls per 10 minutes per call (`tool_transfer` rate-limit bucket), over it → 200 `{ok:false}` without touching Twilio.

**Legacy body token (transition only).** Until the reconcile PATCHes the existing workspace tool, ElevenLabs still sends the old body (`call_token` = the purpose-`'transfer'` token). Those requests are accepted only while the stored tool row exists and is not yet `details.auth = 'headers'` (or a pinned tool has no reconciled row). Once closed, the window stays closed on that instance (re-checked every 30 s while open); a DB error closes it (fails closed). Run `POST /api/admin/voice/tools` right after the deploy to close it at once.

## 3. Race-safe creation (lease rows)

1. `claimResourceLease`: `upsert({key, external_id: '', status: 'creating', lease_owner, lease_until}, {onConflict: 'key', ignoreDuplicates: true})` (= `INSERT … ON CONFLICT DO NOTHING RETURNING`): exactly one caller gets the row. An expired lease (crashed creator) is taken over with `UPDATE … WHERE status='creating' AND lease_until < now()`. Lease: 60 s.
2. The winner first **adopts** a tool left behind by a crash: `GET /v1/convai/tools?search=transfer_to_human&types=webhook` (name prefix, ≤ 5 pages), matching `tool_config.api_schema.url` exactly (so another deployment's tool is never adopted), then PATCHes it; otherwise POSTs (NO_RETRY). Secrets: `GET /v1/convai/secrets?search=<name>`, exact name.
3. `completeResourceLease`: `UPDATE … SET external_id, status='ready' WHERE status='creating' AND lease_owner=<me>`. If that matches nothing, another creator finished first: the duplicate we just created is deleted (`DELETE /v1/convai/tools/{id}?force=false`, not referenced yet) and theirs is used.
4. A failed creation deletes its own lease row (conditional on owner), so the next attempt can claim at once. Losers poll up to 6 s for the winner, then fail with `conflict` (the sync is degraded and retried).
5. When a tool already exists and only a **transient** failure (timeout, network, 5xx, 429, open circuit, conflict) prevents verifying or PATCHing it, the existing tool is kept (`unverified`): it served calls until now. Non-transient failures (validation, auth, permission, not configured) are thrown.

Per-instance memo: a verified tool is trusted for 10 minutes on the sync path, but only while the stored row still holds the same id and config hash (one primary-key read per sync). Any failed agent write that referenced the tool invalidates the memo. The secret id is always read from the row (never memoized) so a secret recreated elsewhere is never overwritten by a stale id.

## 5. Migration 016 (`supabase/migrations/016_platform_tools.sql`)

* `platform_resources`: `status text NOT NULL DEFAULT 'ready'` (`'creating' | 'ready'`), `lease_owner text`, `lease_until timestamptz`, `checked_at timestamptz`, `monitor jsonb NOT NULL DEFAULT '{}'`. Constraints (each in a `DO … EXCEPTION WHEN duplicate_object` block): status enum; a ready row has a non-empty id; a creating row has a lease. RLS stays on with no policy; `REVOKE ALL … FROM anon, authenticated` (service role only). No function, no trigger, no DROP.
* **Verified** on a throwaway PostgreSQL 16 with Supabase-like roles: 001–015, then pre-existing rows, then 016 twice. Existing rows became `ready`; the insert-if-absent claim is won by exactly one caller; a live lease is never taken over, an expired one is; only the lease owner completes; all three constraints reject bad rows; `authenticated` and `anon` get `permission denied` on select/update; the `calls` claim (`outcome IS NULL OR outcome <> 'transferred'`) succeeds once and then returns no row. `tests/migrations/016-platform-tools.test.ts` checks the file statically.
* **Deploy order:** apply 016 before deploying. Without it, creating a tool or secret fails (the agent sync is degraded with a clear error), reading existing rows keeps working.

## 7. UI and admin changes

No dashboard UI change. Tenants see an agent whose transfer tool could not be set up as **Degraded** in the existing status card, with the message "Human transfer is unavailable on calls to your app-routed numbers right now: your agent offers to take a message instead. This is retried automatically."

Admin:
* `POST /api/admin/voice/tools {resync_degraded?: boolean, limit?: 1–50}`: verifies the secret and every platform tool (rotation, PATCH, recreate), audited (`voice.platform_tools.reconciled`), same-origin, rate limited (20/h platform-wide). With `resync_degraded`, re-syncs agents degraded by `transfer_tool_unavailable` once the tool is back. Returns statuses and internal agent ids only.
* `GET /api/admin/voice/diagnostics`: new `platform_tools` section (secret configured/stored/rotated, per tool: pinned, stored, status, `config_current`, header auth, last check, stored monitor) and problems: missing/short secret, agents degraded by the tool, stale config, error spike, missing references, missing or stale (> 48 h) monitoring. `?probe=1` adds live checks (rate limited 20 per 10 min). `platform_resources` now lists `elevenlabs.tool_secret`.
* Maintenance: new first step `platform_tools` (reconcile, executions summary, dependent agents, repair), before `agent_sync_retries`.

## 8. Deploy and manual staging verification (no live calls are automated)

Deploy: (1) apply migration 016; (2) set `ELEVENLABS_TOOL_SECRET` in every environment; (3) deploy; (4) `POST /api/admin/voice/tools {}` (creates the secret, PATCHes the transfer tool to header auth, closes the legacy window); (5) `POST /api/admin/voice/rollout {"dry_run": false}` in batches, or let maintenance push version 2; (6) `GET /api/admin/voice/diagnostics?probe=1` shows no `PLATFORM_TOOLS` error.

1. `GET /v1/convai/tools/{id}`: `execution_mode: post_tool_speech`, `pre_tool_speech: force`, `interruption_mode: disable_during_tool`, `tool_error_handling_mode: passthrough`, `tool_call_sound: null`, `follow_redirects: false`, the two request headers (secret locator, secret variable), the response filter, and no `call_token` in the body. Record whether the API returns the header locators unchanged (else maintenance PATCHes daily; see limitations).
2. `GET /v1/convai/secrets`: one `ntv_tool_key_<env>_<hash>`; `GET …/dependencies/tools` lists the transfer tool. The value is never shown.
3. App-routed call, ask for a person: the agent says it is transferring, finishes the sentence, then the call rings the destination. In the conversation's tool call, the `X-NTV-Call-Token` header must be resolved (not the literal variable) and redacted in transcripts/webhooks; `reason` is the only body field.
4. Turn transfer off (or remove the number) during a call and ask again: the agent says it cannot transfer and offers to take a message (ok:false passthrough).
5. Ask for a transfer twice in quick succession (or provoke a retry): logs show one redirect and `router.transfer_already_claimed`; the call is not dropped.
6. Delete the transfer tool in the dashboard, run `POST /api/admin/voice/tools`: action `recreated`; the next rollout/sync updates agents (`tool_ids`), and the diagnostics dependents check returns to 0 missing.
7. Change the tool's execution mode in the dashboard, run maintenance or the admin endpoint: action `patched` (remote drift).
8. Rotation: set `ELEVENLABS_TOOL_SECRET_PREVIOUS` to the old key and `ELEVENLABS_TOOL_SECRET` to a new one, deploy, run the admin endpoint (`tool_secret.rotated` in logs), place a transfer, then remove the previous key.
9. Mixed org (native + app-routed numbers): on the native number, ask for a person: `transfer_to_number` is used and announced, the caller cannot interrupt it. If the model calls `transfer_to_human` there, it gets ok:false (placeholder token `'none'`).
10. With a scratch tool built from `lib/elevenlabs/tools` (assignments + response filter), check whether assignments run before the response filter (needed by B2's offered slots).
11. On staging, set a wrong `ELEVENLABS_TOOL_SECRET` without reconciling, place 3+ transfer attempts: executions show `customer_auth`/HTTP errors, maintenance logs `platform_tool.error_spike`, diagnostics report the spike.
12. Production without the secret (staging with `NODE_ENV=production`): diagnostics error, agents degraded with the tenant message, the prompt no longer offers transfers.

## 9. Remaining limitations

* Warm-transfer whisper to the human is not implemented (telephony slice).
* Calls already in progress when the tool switches to header auth carry an A2-era `secret__ntv_call_token` (purpose `transfer`) and cannot transfer; they get the "offer a message" guidance. The window is the length of the calls in flight at the reconcile.
* Header-locator round-trip, secret placeholders on agents, the dependent-agents semantics (branches) and the assignment/response-filter order are **unverified live**. If the API normalizes the fields `remoteToolDrift` compares, maintenance PATCHes the tool once per run (harmless, logged).
* Execution counts are capped (500 errors, 1,000 executions per 24 h, `truncated: true`); the rate is then approximate.
* The tool memo means a dashboard deletion is noticed on the sync path within 10 minutes (immediately after a failed agent write, and at every maintenance run).
* The spike event reuses the `health_check` provider-event kind (`operation: tools.executions`) to leave the shared telemetry union untouched.
* `lib/voice-providers/reconcile.ts` does not check tool references (diagnostics and maintenance do).
* The correlation token keeps the historical purpose name `'transfer'`.
