# Slice B2: in-call business tools (appointment booking, take a message, SMS action)

This slice gives the live agent its first business tools: it reads the business's real Google Calendar and books one of the times it offered (`check_availability`, `book_appointment`), and it saves a structured message for the team and alerts them straight away by e-mail (`take_message`). It also adds the missing post-call workflow action **Text the caller** (`send_sms`), which failed on every run before.

The scheduling and tool logic is **ported** from commit e7c7974 (`lib/scheduling/{bookings,slots,text}.ts`, the handler logic of `lib/voice/tools/{calendar,messages,notify,schemas}.ts`), not rewritten. What changed in the port is listed per file in their headers: rules come from the agent's settings, the KV lease became a Postgres lease row, a daily cap was added, the database client is passed in, errors go to the structured logger, and the gateway authentication was replaced by the slice B1 platform tool authentication.

Every ElevenLabs field below was checked against the official OpenAPI document through the B1 builder and `tests/elevenlabs-spec-contract.test.ts` (which validates every platform tool config, including the three new ones, against `WebhookToolConfig-Input`). Vendor behaviour that can only be confirmed with a live call is marked **unverified live**.

## 2. How a tool request is trusted

Same model as slice B1, for all three ElevenLabs tools (`app/api/telephony/tools/_lib/business-tool.ts`):

1. Body: JSON object, at most 8 KB (400/413/415 otherwise).
2. Platform authentication (`authenticateToolRequest`): `X-NTV-Tool-Key` (workspace secret, constant-time compare) and `X-NTV-Call-Token` (`secret__ntv_call_token`, signed, purpose `'tool'`). 401 only for unauthenticated requests.
3. Per-call budget (`allowToolCall`): `check_availability` 10, `book_appointment` 5, `take_message` 5 per call per 10 minutes. Over it: 200 `{ok:false}` telling the model to stop.
4. Call context (`lib/voice-tools/call-context.ts`): the call row from the token's call id; the organisation, agent, settings, calendar id, caller number and business number all come from the database, scoped by the call's own `org_id`. Unknown calls, calls without an agent and **ended calls** (more than 60 s after `ended_at`, or a terminal status) are rejected with guidance.
5. The tool. The body is only the model's arguments, validated with tolerant zod schemas (`lib/voice-tools/schemas.ts`): blanks become null, enums are coerced, long text is shortened, unknown keys (including any `org_id`, `calendar_id`, `call_id` or phone number the model invents) are ignored.

Every expected failure is HTTP 200 `{ok:false, message}` with safe guidance (`tool_error_handling_mode: 'passthrough'`). Messages never contain internal ids, error texts or full phone numbers (the callback number is read back as its last four digits).

Native inbound calls (ElevenLabs-owned numbers) carry no tool token (`ntv_call_id` is `"unknown"`, the token placeholder is `"none"`): the prompt tells the agent not to call the tools then and to take details by voice; a call anyway gets a generic `{ok:false}`.

The Cartesia fallback tool (`/api/telephony/tools/cartesia-message`) cannot carry our token over SIP: it is authenticated by the static bearer `CARTESIA_TOOL_SECRET` (constant time) and the call is found from the Cartesia system variables `system__called_number` and `system__caller_id` (the model cannot change them): the called number gives the org (our `phone_numbers` row), then the most recent live Cartesia call on that number from that caller (2 h window). Same budget, context loading, idempotency and alert as the ElevenLabs tool.

## 3. Booking rules (lib/scheduling)

* Slots: `generateSlots` (ported) inside the agent's working hours (or the default business hours when none are set), `duration_minutes` (5–240, default 30), `buffer_minutes` (0–120), `booking_window_days` (1–365, default 30), `min_notice_hours` (0–168, default 2), optional `daily_cap` (1–100). Busy = Google free/busy plus our own active bookings (covers events Google does not show yet). An empty range looks up to 7 more days ahead (and relaxes the time-of-day preference) so one call can still offer something.
* Slot ids: `s` + local `YYYYMMDDHHmm` (deterministic). Offered slots are stored in `call_slot_offers (call_id, slot_id)`.
* Booking: offered on this call → idempotency check → per-org lease (`booking_locks`, 30 s TTL, 8 attempts 350 ms apart, expired leases taken over) → idempotency re-check → fresh busy check and rule re-check (`explainRejectedStart`: in the past, too soon, beyond the window, outside hours, day full, taken) → `pending` row (holds the time; unique index `bookings_active_slot`) → `events.insert` (`sendUpdates: 'none'`, no retry, 8 s timeout, private extended properties `ntv_booking_id`, `ntv_call_id`) → `booked`. A failed or timed-out insert first looks for the event by `privateExtendedProperty` (recovery), otherwise the pending row is deleted: **a time is never confirmed unless the event exists**. A Google auth error marks the integration as needing reconnection.
* Test calls get `[Test]` in the event title and a note in the description.

## 4. Endpoints and fields

ElevenLabs (through the B1 modules, no new wrapper): `POST /v1/convai/tools` (NO_RETRY), `GET/PATCH /v1/convai/tools/{id}`, `GET /v1/convai/tools?search=…` (adoption), `DELETE /v1/convai/tools/{id}?force=false` (lost race), plus the agent body:

* `conversation_config.agent.prompt.tool_ids`: transfer tool (when app-routed) followed by the attached business tools.
* `conversation_config.agent.dynamic_variables.dynamic_variable_placeholders.ntv_offered_slots = []` when the booking tools are attached (the allowed-values list is empty until slots are offered).
* `PLATFORM_AGENT_CONFIG_VERSION` is now 3 (config rollout re-pushes existing agents).

Tool configs (`WebhookToolConfig-Input`): `name`, `description`, `response_timeout_secs` (READ 8 s, WRITE 15 s), `execution_mode: 'immediate'`, `pre_tool_speech` (READ `auto`, WRITE `force`), `interruption_mode: 'disable_during_tool'`, `tool_error_handling_mode: 'passthrough'`, `tool_call_sound: 'typing'`, `tool_call_sound_behavior: 'auto'`, `follow_redirects: false`, `assignments[] {source:'response', dynamic_variable, value_path, sanitize, preserve_native_type}` (check_availability only), `api_schema {url, method:'POST', content_type, request_headers {X-NTV-Tool-Key: {secret_id}, X-NTV-Call-Token: {variable_name:'secret__ntv_call_token'}}, request_body_schema, response_filter {mode:'allow', filters}}`. `book_appointment.slot_id` uses `allowed_values {dynamic_variable}` with a description source (the deprecated `allowed_values_dynamic_variable` is never written).

Cartesia: `POST /v1/agents/tools` (NO_RETRY) for the `take_message` webhook tool (`api_schema.authentication {mode:'bearer', token:{type:'secret'}}`, body properties with `dynamic_variable: system__called_number / system__caller_id`), platform resource `cartesia.message_tool`; the agent's `tools` list carries it next to the context tool when messages are enabled.

Google Calendar (`googleapis` calendar v3, the org's own OAuth token): `freebusy.query`, `events.insert`, `events.list` (`privateExtendedProperty`, recovery), `calendarList.list` (calendar picker, writability check: `owner`/`writer` only).

Twilio (platform account): `IncomingPhoneNumbers(sid).fetch()` (`capabilities.sms`, cached on the number for 24 h), `messages.create({from, to, body})`. Error 21610 records an opt-out.

## 5. Migration 018 (`supabase/migrations/018_business_tools.sql`)

Additive and idempotent, no DROP of any kind.

* `agents.booking_settings`, `agents.message_settings` (jsonb, default `{}`); `phone_numbers.sms_capable`, `phone_numbers.sms_checked_at`. Guarded by the new `public.guard_b2_columns()` (triggers `agents_guard_b2` on INSERT/UPDATE, `phone_numbers_guard_b2` on UPDATE): a tenant JWT cannot write them; the API writes them with the service role after validation. `guard_platform_columns()` is untouched.
* `bookings` (status `pending|booked|cancelled`, source `voice_tool|dashboard`, unique `bookings_idempotency (org_id, idempotency_key)`, unique `bookings_active_slot (org_id, calendar_id, starts_at) WHERE status IN ('pending','booked')`).
* `booking_locks`, `call_slot_offers`, `tool_invocations` (unique `(call_id, tool, idempotency_key)`): internal, RLS on, no policy, no tenant privileges.
* `call_messages` (one per call, `ON DELETE CASCADE` from `calls` so a privacy deletion removes it; `notify_count`, `notify_error`, `notified_at`).
* `sms_messages` (unique `(org_id, idempotency_key)`), `sms_opt_outs` (PK `(org_id, phone)`).
* RLS on every new table; tenants may SELECT their own `bookings`, `call_messages`, `sms_messages`, `sms_opt_outs` (`org_id IN (SELECT id FROM organizations WHERE user_id = (SELECT auth.uid()))`); every write goes through the service role.
* `public.apply_business_tool_retention(p_agent_id, p_cutoff, p_limit)`: clears names, numbers, reasons, notes and texts older than the cutoff (bounded, `FOR UPDATE SKIP LOCKED`, idempotent). `SET search_path = public`; `EXECUTE` revoked from `PUBLIC, anon, authenticated`.
* **Verified** on a throwaway PostgreSQL 16 with Supabase-like roles: 001–018, then 018 again; double booking refused, idempotency key unique, one message per call, urgency enum, tenant SELECT scoped to its org, tenant writes refused on every new table, the guarded columns refused for tenant JWTs, retention not executable by tenants, bounded to the org and idempotent, call deletion cascades to messages but not bookings. `tests/migrations/018-business-tools.test.ts` checks the file statically.

**Deploy order:** apply 018 **before** deploying this code. Without it, the agent sync reads the settings as "everything off" (`42703` handled) and the new routes fail closed.

## 8. Deploy and manual staging verification (no live calls are automated)

Deploy: (1) apply migration 018; (2) deploy; (3) `POST /api/admin/voice/tools {}` creates and reconciles the three new platform tools (or let maintenance do it); (4) `POST /api/admin/voice/rollout {"dry_run": false}` or let maintenance push config version 3.

1. `GET /v1/convai/tools/{id}` for each new tool: behaviour presets, the two request headers, the response filter, the assignment on `check_availability`, `allowed_values {dynamic_variable:'ntv_offered_slots'}` on `book_appointment.slot_id`, no org/calendar/phone field in any body.
2. Agent with booking on and Google Calendar connected: `GET /v1/convai/agents/{id}` shows the tool ids and the `ntv_offered_slots: []` placeholder. Check that ElevenLabs accepts an **empty list** placeholder together with `allowed_values` (**unverified live**).
3. App-routed call: ask for an appointment tomorrow. The agent calls `check_availability`, offers 2–3 times, reads the chosen one back, calls `book_appointment`, and confirms only after `ok = true`. The event appears in the chosen calendar with the caller's name and number; `bookings` has one `booked` row.
4. In the conversation's tool calls, check that `ntv_offered_slots` was filled from `slot_ids` (i.e. the assignment runs **before** the response filter, or on the unfiltered body; **unverified live**, B1 step 10) and that the model could pass the id back.
5. Ask the agent to book a time it did not offer (e.g. "book 3 am"): `ok:false` "not offered on this call"; nothing written.
6. Two phones, same slot at the same time: one booking, the other caller is told it was just taken.
7. Disconnect Google Calendar during a call and ask to book: `ok:false` guidance, the agent offers a message. After the disconnect, the agent is re-synced without the booking tools and its prompt says it cannot book.
8. Take a message with "call me back on 0721 234 567", urgent: the agent reads the number back, `call_messages` has the E.164 number, the alert e-mail arrives with `[URGENT]`, the dashboard card shows it; mark it done.
9. Hang up and replay the same tool request after a minute: `ok:false` "this call has already ended".
10. Fallback path (Cartesia): force the fallback, leave a message: the Cartesia tool resolves the call from the numbers and saves it with `provider: cartesia`.
11. Workflow "Text the Caller" on an org whose number is voice-only: the builder explains why it is not offered; an existing step fails with "your business number cannot send text messages". With an SMS-capable number: one text per call, a second run says "already sent".
12. Native ElevenLabs number (no tool token): ask to leave a message; the agent takes details by voice and does not call the tool.

## 9. Remaining limitations

* **Find / move / cancel a booking by phone** (e7c7974 `find_booking`, `reschedule`, `cancel`) were not ported: matching a caller to an existing booking by caller id alone is spoofable. Owners manage bookings in Google Calendar.
* **Booking on the Cartesia fallback** is not available: the fallback prompt takes the request as a message with `take_message` instead.
* **Calendar changes made in Google** (moving or deleting an event the agent created) are not mirrored into `bookings`; the local row only keeps the time held against parallel bookings until the event's time passes. A pending row older than 10 minutes is released by maintenance; if Google had created the event despite the failure and recovery also failed, that event stays in the calendar without a confirmation to the caller.
* **Message alerts** go by e-mail only. No `message_taken` workflow trigger (needs a CHECK constraint change that requires a DROP) and no Slack alert. Extra recipient addresses are validated but not confirmed by their owners (capped at 5 per agent and by the daily cap).
* **In-call SMS** (`send_sms` tool) and booking confirmation texts are not built. Romanian sender-ID registration and opt-in rules remain the owner's responsibility for workflow texts; the builder states the text must be transactional.
* The Cartesia `take_message` tool is created once and not reconciled (same as the existing context tool): description changes need the platform resource row removed so it is recreated.
* Retention: the agent's privacy retention (minimum 1 day) clears caller details in `call_messages`, `bookings` and `sms_messages`; events already written to the tenant's Google Calendar are the tenant's data and are not edited.
* ElevenLabs keeps tool request bodies in conversation transcripts and tool executions (workspace-level): names, reasons and dictated numbers appear there under the agent's ElevenLabs retention.
* Existing, outside this slice: the dashboard page reads `integrations` with `select('*')` for the client component (includes the Google refresh token column); the Google OAuth connect flow asks for every Google scope at once; `components/workflows/meta.ts` is unused.
* The assignment / response-filter order and the empty-list placeholder with `allowed_values` are **unverified live** (staging steps 2 and 4). If the assignment runs after the filter and `slot_ids` were filtered out it would still work (the filter keeps `slot_ids`); if ElevenLabs rejected the empty placeholder, the agent update fails and the sync is reported degraded.
